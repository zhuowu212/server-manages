# 轻量服务器资产管理系统 Constitution

## Core Principles

### I. 需求与验收先行

每项功能、修复或行为变更 MUST 先明确用户目标、业务行为、边界条件和可验证的验收标准，
再进入技术方案、任务拆分和编码。实现细节、数据库结构或框架限制 MUST NOT 被用来替代
用户需求；需求存在歧义时 MUST 在规格中记录澄清结果或明确的假设。计划和任务 MUST
能够追溯到验收标准，完成声明 MUST 以验收证据为依据。

理由：先固定可观察行为可以减少返工，并使产品决策、技术决策和交付结果保持一致。

### II. 安全与最小权限

系统 MUST 使用本地账号登录，并以经过验证的自适应单向密码哈希安全存储密码，例如
Argon2id 或 bcrypt；密码 MUST NOT 以明文、可逆加密或日志形式保存。所有受保护操作
MUST 在服务端进行身份认证、授权和默认拒绝检查，客户端隐藏按钮不得被视为授权控制。
账号和角色 MUST 只获得完成职责所需的最小权限。

所有外部输入 MUST 在服务端按类型、长度、格式、范围和关联关系校验；数据库访问
MUST 使用参数化接口；输出到浏览器的内容 MUST 按上下文进行编码。SSH 密码和 SSH
私钥 MUST NOT 被系统保存，资产记录仅可保存外部凭据引用。密码、令牌、私钥及其他
秘密 MUST NOT 出现在源代码、提交记录、错误响应、备份明文或日志中。

理由：资产管理系统集中保存基础设施信息，最小权限和服务端控制是降低越权、凭据泄露
和横向影响的必要边界。

### III. 数据完整性与可追溯

资产编号 MUST 在数据库层建立唯一约束，并在用户反馈层提供清晰的冲突信息。虚拟机与
宿主机的关联 MUST 指向存在且类型正确的宿主机；创建、修改和导入 MUST 校验关联有效性，
禁止产生孤儿关联或违反业务关系的数据。导入操作 MUST 对输入格式、必填字段、重复项、
关联项和字段值进行校验，并按规格定义是否整体提交；部分写入不得在未明确告知的情况下
发生。

删除和其他破坏性操作 MUST 同时受到服务端权限检查和明确的二次确认保护，并在执行前
检查关联、依赖和保留要求。关键变更 MUST 写入审计记录，至少包含操作者、时间、动作、
目标、结果和必要的变更摘要；审计记录 MUST 不包含密码、令牌或私钥。

理由：资产关系错误会直接影响运维判断，审计轨迹则为误操作调查、责任确认和恢复决策
提供依据。

### IV. 分层设计与可维护性

代码 MUST 保持清晰的职责边界；界面层负责交互呈现，业务层负责业务规则，持久化层
负责数据访问，跨层调用 MUST 遵循项目既有接口和依赖方向。业务规则不得只存在于前端，
重复逻辑、隐式副作用和无法解释的特殊分支 MUST 被消除或记录理由。代码、命名和错误
处理 MUST 可读且一致；错误 MUST 被结构化处理，向用户提供安全且可行动的反馈，向日志
提供不泄露秘密的诊断信息。

数据库结构和数据变更 MUST 通过可追踪的迁移或等价版本管理交付；部署新版本时必须
明确兼容性、升级顺序和失败处理。新增抽象只有在降低真实复杂度、减少有意义的重复或
符合既有模式时才可引入。

理由：清晰边界和可追踪变更降低维护成本，使小规模团队能够安全演进系统。

### V. 自动化验证与可重复运维

关键业务规则、服务端权限、虚拟机与宿主机关系、导入校验以及备份恢复 MUST 有自动化
测试。涉及共享行为或跨模块契约的变更 MUST 补充相应的集成或契约测试。测试、类型
检查、静态检查和构建中的必需项失败时，功能 MUST NOT 被宣称为完成。

Docker Compose MUST 支持可重复部署；运行所需配置和秘密 MUST 通过明确的环境配置或
外部秘密引用注入，不得硬编码进镜像或仓库。备份 MUST 可执行恢复验证，不能仅以备份
文件存在作为成功标准。日志 MUST 避免记录密码、令牌、私钥和完整外部凭据。

理由：自动化验证把关键约束变成持续可检查的证据，可重复部署和可恢复备份则保证系统
在小团队运维条件下仍然可控。

## Additional Constraints

- 系统面向小规模团队，管理后台 MUST 提供中文界面；用户可见的标签、状态、错误、成功、
  空状态和确认信息 MUST 使用清晰一致的中文表达。
- 关键操作 MUST 提供明确反馈，包括成功、失败、进行中和无数据状态；错误反馈 MUST 指出
  可采取的修正方向，但不得泄露内部堆栈、凭据或安全配置。
- 管理界面 MUST 支持合理的键盘操作、可识别的表单标签、足够的颜色对比和清晰的焦点
  状态；信息、状态和权限不得只依赖颜色表达。
- 破坏性操作 MUST 使用明确的动作名称进行二次确认；确认文案 MUST 说明目标和不可逆
  影响，取消操作 MUST 保持数据不变。
- 本地账号、角色和权限模型 MUST 与实际服务端授权规则一致；新增登录方式或外部身份
  提供商必须先通过需求和安全评审，不得默默扩大认证边界。

## Development Workflow

- 需求阶段 MUST 使用 Spec Kit 规格明确行为和验收标准；技术方案 MUST 说明数据、授权、
  错误处理、测试和运维影响；任务 MUST 按依赖关系拆分并关联到验收标准。
- 实现前 MUST 识别涉及的安全、数据完整性、权限、审计、导入和备份恢复约束；实现后
  MUST 执行与变更风险匹配的自动化测试、类型或静态检查、构建检查及必要的最小冒烟测试。
- 每项功能的完成判定 MUST 包括验收标准、测试结果和已知限制。任何必需测试失败、
  验收条件未满足或关键验证无法执行时，MUST 明确报告未完成状态，不得宣称完成。
- 实现完成后 MUST 按 Spec Kit 执行收敛检查（`$speckit-converge`），确认规格、计划、
  任务和代码一致；发现遗漏的工作 MUST 回写任务清单并继续处理。
- 评审 MUST 检查服务端授权、输入校验、秘密处理、数据库约束、审计记录、破坏性操作、
  迁移、自动化测试、备份恢复和日志内容；偏离本宪法的决定 MUST 记录理由、范围、负责人
  和到期复查时间。

## Governance

本宪法是需求、技术方案、任务、实现、评审和运维决策的长期约束；其他实践与其冲突时，
MUST 先修订本宪法或记录经批准的例外。修改宪法 MUST 说明动机、影响范围、受影响原则、
迁移或后续行动，并更新顶部的 Sync Impact Report。项目负责人或指定维护者 MUST 在修改
生效前完成审阅；宪法修改不得借机删除无关原则。

版本号遵循语义化版本：删除或重新定义既有原则、造成治理不兼容时递增 MAJOR；新增
原则或实质扩展约束时递增 MINOR；仅澄清措辞、修正错误或进行不改变约束的格式调整时
递增 PATCH。版本、批准日期和最后修订日期 MUST 使用 ISO `YYYY-MM-DD` 格式。

每次 Spec Kit 规格、计划、任务生成和实现收敛 MUST 检查本宪法的适用条款；代码评审
和发布前检查 MUST 记录关键质量门槛的验证结果。自动化测试失败、备份恢复验证失败或
安全约束未满足时，发布 MUST 暂停，直到问题修复或经批准的例外被记录。
